# virtualUSB error map

Match the client's output (stdout and stderr together) against the **Symptom** column, then report `<Meaning> → <Next step>` in plain language. Never retry the same command in a loop; each row says whether one retry is allowed. `vusb` exit codes are not a reliable signal — parse the text.

| Symptom (exact / regex) | Meaning | Next step |
|---|---|---|
| `Authorization info not found. Please login to your Kobiton's account first!` (printed by `connect`, `disconnect`, `status`) | The client has no saved sign-in on this machine | Run `~/.kobiton/bin/vusb login` (the wrapper injects `--apibaseurl`, `--username`, `--apikey` from `~/.kobiton/.credentials`), then retry the failed command once. If `login` itself fails with `Missing KOBITON_…`, run `/automate:doctor`, then `/automate:setup`. |
| `Login failed:` (for example `Invalid username/email or API key`), or `Authentication error:` with anything other than the row above (invalid key, 401, 403) | The saved API key was rejected | Run `/automate:setup` to refresh `~/.kobiton/.credentials`, then `~/.kobiton/bin/vusb login` again. Stop if it fails a second time. |
| `virtualUSB is not included in your current subscription` | The organization's plan has no virtualUSB add-on | Stop. Tell the user their Kobiton organization admin must enable virtualUSB on the subscription; nothing on this machine fixes it. |
| `virtual_usb_status.state = DISABLED` (from `listHostingMachines` for a not-ready device) | virtualUSB is turned off on this device's host machine | Stop. Enable virtualUSB for the machine (quote `host_name` when non-null) in Portal → Device Management; an admin can instead confirm and use `configureHostingMachine` (SKILL.md Step 3). |
| `virtual_usb_status.state = NO_NETWORK_ROUTE` (from `listHostingMachines`) | virtualUSB is on, but no network route is configured for the host machine | Stop. Choose a routing option (Kobiton-managed or a custom address) in Portal → Device Management; an admin can instead confirm and use `configureHostingMachine` (SKILL.md Step 3). |
| `virtual_usb_status.state = ROUTING_PROVISIONING` (from `listHostingMachines`) | Kobiton-managed routing for this machine is still being set up | Stop. Wait a few minutes, then check again with `listDevices({virtualUsb: true, udid})`. |
| `virtual_usb_status.state = ROUTING_PROVISIONING_FAILED` (from `listHostingMachines`) | Setting up Kobiton-managed routing for this machine failed | Stop. Retry routing setup in Portal → Device Management, or contact Kobiton support. |
| `virtual_usb_status.state = CONFIGURED` but `listDevices` still reports `virtual_usb_ready: false` | The host machine is configured, but the device isn't ready for virtualUSB yet | Stop. Relay `next_step`: check again shortly; if it persists, contact Kobiton support. |
| `sku_note` present (from `listHostingMachines`, `sku_active: false`) | Your organization doesn't have the virtualUSB add-on | Stop. Relay `sku_note`: contact your Kobiton account team to add it. |
| `listHostingMachines` fails with `You don't have permission to do this action.` | Only an organization admin can see this device's host machine | Stop. Ask an organization admin to check the host machine in Portal → Device Management. |
| `listHostingMachines({udid})` returns empty `machines` with a `reason` | The device isn't among your private devices, or its host machine isn't visible to your role | Stop. Relay `reason`; an admin with access to all devices can check Portal → Device Management. |
| `listHostingMachines({udid})` returns a machine with `device.is_hidden = true` or `device.state = UNPLUGGED`, and a `reason` | That machine is not where the device is connected: the device is hidden there in Portal → Device Management, or unplugged from it | Stop. Relay `reason`; do not configure that machine. Ask whoever manages the device's current host to check it in Portal → Device Management. |
| `configureHostingMachine` fails with `Organization does not have the virtualUSB SKU` | Your organization doesn't have the virtualUSB add-on | Stop. Contact your Kobiton account team to add it. |
| `configureHostingMachine` with `virtualUsb.networkRouting: KOBITON` fails because Kobiton-managed routing is not available for the organization | Kobiton-managed routing isn't offered for your organization | Offer self-managed routing with the machine's reachable IP address instead; otherwise stop and contact Kobiton support. |
| `configureHostingMachine` rejects the IP address as invalid | The address given for self-managed routing is not a valid IP address | Ask the admin for the machine's correct reachable IP address and retry once. |
| `configureHostingMachine` rejects `virtualUsb.networkRouting: SELF_MANAGED` without `virtualUsb.ipAddress` (or `virtualUsb.ipAddress` with `KOBITON`) | Self-managed routing needs the machine's IP address; Kobiton-managed routing takes none | Ask the admin for the IP address (or drop it for Kobiton-managed) and retry once. |
| `configureHostingMachine` fails with `machine <id> is not among the host machines your role can see` | The machine id is wrong, or the machine isn't visible to your role | Re-run `listHostingMachines({udid})` and use the returned `id`; if it is still missing, stop. |
| `configureHostingMachine` fails with `You don't have permission to do this action.` | Only an organization admin can configure a host machine | Stop. Ask an organization admin to configure it. |
| `Failed to connect to dcb app server: Connection refused` (inside `Failed to get status: DcbStatusError { … }`) | The client's background daemon is not installed or not running yet | On macOS the first `vusb connect` (and every version bump) installs the daemon through an administrator dialog in the GUI session — run `connect`, tell the user to approve the dialog, do not retry `status` in a loop. Over SSH / without a GUI session the daemon cannot be installed: stop and hand off. On Windows, run `vusb setup-adb` in an administrator terminal (see the preflight hand-off steps). |
| `Connect failed:` + `timed out`, `unreachable`, `connection reset`, `no route to host`, `dns`, `TLS` | The device's host machine cannot be reached from this network | Check VPN / proxy on this machine, then confirm the host machine's virtualUSB routing in Portal → Device Management (the machine that hosts the device). Retry `connect` once after the network changes; otherwise stop. |
| `Connect failed: Failed to retain device:` + `in clean up process` | The platform is still cleaning the device up after its last session - often this session's own disconnect; it takes a few minutes | Not another holder: don't describe it as in use. The `connect` process has already exited, so there is nothing to tear down. Offer to wait: poll `getDeviceStatus({deviceId})` every 30 s for up to 10 minutes until `is_booked: false`, then `connect` once more; or pick another ready device. |
| `already retained`, `already connected`, `in use`, `booked`, `is being used by` | Another session or user holds the device (manual, automation, or another virtualUSB client) | Do not wait on it. Offer `listDevices({virtualUsb: true})` to pick another ready device, or tell the user to ask the holder (or a Portal admin) to release it. |
| `vusb --version` token ≠ the pin in `VUSB_VERSION`, or the wrapper prints `Warning: pinned virtualUSB version … is not cached` | The client in use is not the build this plugin release was validated against | Re-run the preflight: `bash <plugin-root>/skills/debug-device-over-vusb/scripts/vusb-preflight.sh`. If it reports `handed off to human`, relay its stderr (system install at another version, or the pin is no longer published — update the automate plugin). |
| Picked device `platform_name: "iOS"` while `uname -s` is `MINGW*`/`MSYS*`/`CYGWIN*` | iOS devices are list-only on a Windows host | Stop before `connect` unless the user only wants the device listed; direct them to a macOS host for Xcode-based debugging. |
| `vusb status` shows the device connected, but `adb devices -l` does not list it | The local adb server started before the virtual device appeared | Run `adb kill-server`, `sleep 3`, `adb devices -l` once. Still empty → `~/.kobiton/bin/vusb disconnect --udid <udid>` then `connect` once more. Still empty → stop and report; leave the device disconnected (Step 9). |
| `adb: device unauthorized` / `unauthorized` in `adb devices -l` | The device has not trusted this computer's adb key | Tell the user to accept the "Allow USB debugging" prompt on the device's screen (via the Portal live view if needed), then re-check `adb devices -l` once. |
| `error: The following required arguments were not provided: --udid <udid>` | `connect` / `disconnect` was called without the UDID | Re-issue the command with `--udid <udid>` from the picked device. |
| Preflight exit 1 with `is not signed by Kobiton (Developer ID Installer, team 4X2699AQKX)` or `failed code-signature verification` | The downloaded client is not Kobiton's signed build (tampered download or mirror) | Stop; do not retry from the same source. Report it on the plugin repository with the preflight output. |
| Preflight stderr `the cached build <pin> failed verification (signature or version); downloading it again` | The cached bundle was altered or is not the pinned build | Informational: the preflight re-downloads and verifies it; continue with its `outcome=`. |
| Preflight exit 1 with `checksum mismatch for macos.pkg (<version>) - download discarded, existing cache untouched.` | The downloaded package did not match its published sha256 (corrupted or tampered) | Retry the preflight once; if it repeats, stop and report it on the plugin repository. Any existing cache is intact. |
| Preflight exit 1 with `could not fetch checksum for <version> (HTTP <code>) - refusing unverified install.` | The `.sha256` sibling could not be fetched, so the download cannot be verified | Retry once when the network is stable; otherwise stop. Nothing unverified is ever installed. |
| Preflight `outcome=redirected (limitation)` | This host OS is not supported by the skill | Stop; see `references/limitations.md` (Linux host). |
